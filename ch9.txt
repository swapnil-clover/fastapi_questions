
Chapter 9: Completing CRUD — Update and Delete (PUT, PATCH, DELETE) in FastAPI
By OTLMS / August 10, 2026
Let’s Start With a Real Problem

Your app has been live for a week. A user emails support: “I made a typo in my email address during signup — can you fix it?” You open your API… and realize you never built an update endpoint. The only tools you have are “create” and “read.” The only way to “fix” that email is to manually edit the database by hand, or tell the user to delete their account and start over.

CRUD stands for Create, Read, Update, Delete — and so far in this series, we’ve only built the C and the R. This chapter completes the picture. You’ll learn the real difference between PUT and PATCH (a distinction almost every beginner gets wrong at least once), and how to delete data safely, including data with relationships attached to it.
What You’ll Learn

    The real, spec-accurate difference between PUT and PATCH
    How to build a full-replacement update endpoint with PUT
    How to build a partial-update endpoint with PATCH, updating only the fields the client actually sent
    How to safely delete a resource with DELETE, and what happens to related data
    Theory + hands-on assignment questions to lock in what you’ve learned

We’ll continue using SQLAlchemy and SQLite, exactly as set up in Chapter 8.
Theory: PUT vs. PATCH vs. DELETE
Method	Purpose	Client Sends	Behavior
PUT	Replace a resource entirely	The complete new representation	Any field not included is expected to be reset/cleared
PATCH	Partially update a resource	Only the fields being changed	Fields not included stay exactly as they were
DELETE	Remove a resource	Usually nothing (just the ID in the URL)	The resource (and possibly related data) is gone

This trips up a lot of developers: PUT is meant to be a full replacement. If your API’s PUT /users/5 only receives {"email": "new@example.com"}, spec-correct behavior would treat every other field as unset. In practice, many real-world teams relax this rule for convenience — but it’s important you understand the correct behavior first, which is exactly what Program 1 demonstrates, before you decide to bend it.

PATCH, by contrast, was designed exactly for the “I just want to change one field” use case — which is why it’s usually the better fit for real-world edit forms.

app/services/user_service.py

from sqlalchemy.orm import Session

from app.models.user import User
from app.schemas.user import UserCreate, UserReplace


def create_user(db: Session, user_in: UserCreate) -> User:
    new_user = User(
        username=user_in.username,
        email=user_in.email,
        hashed_password=f"hashed_{user_in.password}",
    )
    db.add(new_user)
    db.commit()
    db.refresh(new_user)
    return new_user


def get_user_by_id(db: Session, user_id: int) -> User | None:
    return db.get(User, user_id)


def replace_user(db: Session, user_id: int, data: UserReplace) -> User | None:
    user = db.get(User, user_id)
    if user is None:
        return None

    # Full replacement: every editable field is overwritten, no partial merging.
    user.username = data.username
    user.email = data.email
    user.is_active = data.is_active

    db.commit()
    db.refresh(user)
    return user

app/routers/users.py

from fastapi import APIRouter, Depends, HTTPException, status
from sqlalchemy.orm import Session

from app.db.database import get_db
from app.schemas.user import UserCreate, UserOut, UserReplace
from app.services.user_service import create_user, get_user_by_id, replace_user

router = APIRouter(prefix="/users", tags=["Users"])


@router.post("/register", response_model=UserOut, status_code=status.HTTP_201_CREATED)
def register_user(user_in: UserCreate, db: Session = Depends(get_db)):
    return create_user(db, user_in)


@router.get("/{user_id}", response_model=UserOut)
def get_user(user_id: int, db: Session = Depends(get_db)):
    user = get_user_by_id(db, user_id)
    if user is None:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="User not found.")
    return user


@router.put("/{user_id}", response_model=UserOut)
def update_user_full(user_id: int, data: UserReplace, db: Session = Depends(get_db)):
    user = replace_user(db, user_id, data)
    if user is None:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="User not found.")
    return user

app = FastAPI(title=settings.app_name, version=settings.app_version)

@app.get("/", tags=["Root"])
def read_root():
    return {"message": f"Welcome to {settings.app_name}"}

Detailed Code Explanation

    UserReplace is a dedicated schema, separate from UserCreate — notice it has no password field. Passwords are updated through their own dedicated flow in real apps (covered later in the authentication chapters), never bundled into a generic profile update. Every field in UserReplace is required, not optional — that’s what makes this a true PUT: the client must state the full new picture.
    replace_user simply overwrites username, email, and is_active directly — no merging, no “keep the old value if not sent” logic. That’s the defining trait of PUT.
    The router uses @router.put("/{user_id}", ...) — FastAPI provides @router.put() just like @router.get() and @router.post(), mapping directly to the HTTP PUT method.
    We reuse the exact HTTPException pattern from Chapter 7 for the “not found” case — by now, this should feel like a familiar, repeatable pattern across your whole API.

Execution & Testing

uv run fastapi dev app/main.py

    Call PUT /users/{user_id} with a full body, e.g. {"username": "amitk", "email": "amit.k@example.com", "is_active": true}. Confirm the response shows the updated values.
    Try calling PUT /users/{user_id} with a field missing (e.g., no is_active) — Swagger UI will show a 422 validation error, since PUT requires the complete representation.

app/services/user_service.py

from sqlalchemy.orm import Session

from app.models.user import User
from app.schemas.user import UserCreate, UserPatch


def create_user(db: Session, user_in: UserCreate) -> User:
    new_user = User(
        username=user_in.username,
        email=user_in.email,
        hashed_password=f"hashed_{user_in.password}",
    )
    db.add(new_user)
    db.commit()
    db.refresh(new_user)
    return new_user


def get_user_by_id(db: Session, user_id: int) -> User | None:
    return db.get(User, user_id)


def patch_user(db: Session, user_id: int, data: UserPatch) -> User | None:
    user = db.get(User, user_id)
    if user is None:
        return None

    # Only apply fields the client actually sent.
    update_data = data.model_dump(exclude_unset=True)
    for field_name, value in update_data.items():
        setattr(user, field_name, value)

    db.commit()
    db.refresh(user)
    return user

Detailed Code Explanation

    UserPatch makes every field optional with default=None. This is the schema-level signal that “the client might send some, all, or none of these fields.”
    The real magic is in patch_user: data.model_dump(exclude_unset=True) builds a dictionary containing only the fields the client actually included in the request body — not the ones that simply defaulted to None. This is a critical distinction:
        If the client sends {"email": "new@example.com"}, exclude_unset=True gives you {"email": "new@example.com"} — username and is_active are left out entirely, because they were never mentioned.
        Without exclude_unset=True, you’d get {"username": None, "email": "new@example.com", "is_active": None} — which would incorrectly wipe out the user’s existing username!
    setattr(user, field_name, value) then applies only those included fields onto the actual database object, one at a time.
    This is precisely why PATCH exists as a separate HTTP method from PUT — it has fundamentally different semantics, not just “a smaller PUT.”

Execution & Testing

uv run fastapi dev app/main.py

    Register a user via POST /users/register.
    Call PATCH /users/{user_id} with just {"email": "updated@example.com"} — confirm the response shows the new email, but the username is unchanged.
    Call PATCH /users/{user_id} again with just {"is_active": false} — confirm only that field changes, and the email you set in step 2 is still there.
    Compare this behavior to Program 1’s PUT, where omitting a field either fails validation or (if you made fields optional) would silently overwrite it — this is the core lesson of the chapter.

        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="User not found.")
    return create_post_for_user(db, user_id, post_in)


@router.get("/", response_model=list[PostOut])
def get_posts(user_id: int, db: Session = Depends(get_db)):
    return list_posts_for_user(db, user_id)

Detailed Code Explanation

    delete_user fetches the user first (so we can tell the difference between “already gone” and “successfully deleted”), then calls db.delete(user) followed by db.commit(). It returns a plain bool so the router can decide what HTTP response to send.
    Because User.posts was defined with cascade="all, delete-orphan" back in Chapter 8, deleting a User row automatically deletes every Post row linked to it — SQLAlchemy handles this at the ORM level, without you writing a separate “delete all posts for this user” query.
    In the router, status_code=status.HTTP_204_NO_CONTENT is set at the decorator level since a successful delete has nothing meaningful to return. We also explicitly return Response(status_code=status.HTTP_204_NO_CONTENT) — for a 204, FastAPI expects no response body at all, and returning an empty Response object avoids accidentally sending one.
    If the user doesn’t exist, we raise the same HTTPException 404 pattern used throughout this series — consistent error handling, even for deletes.
    posts.py includes a GET endpoint for listing a user’s posts, specifically so you can verify the cascade delete actually worked during testing.

    ⚠️ Important: Cascade behavior (cascade="all, delete-orphan") is an ORM-level setting — it only takes effect when you delete through SQLAlchemy, as we’re doing here. If someone deletes rows directly via raw SQL or a database GUI tool, this Python-level cascade won’t run. For strict guarantees at the database layer itself, you’d also configure ON DELETE CASCADE on the foreign key — worth knowing as you move toward production, though outside the scope of this chapter.

Tips & Instructions for Developers

    ✅ Use PUT only when the client is expected to send the complete resource — and make every field in that schema required, so FastAPI enforces this for you.
    ✅ Use PATCH with exclude_unset=True whenever you want true partial updates — this is the pattern you’ll use most often for real-world “edit profile” style forms.
    ✅ Always fetch the record first before updating or deleting it, so you can return a proper 404 instead of silently doing nothing.
    ✅ Return 204 No Content for successful deletes — there’s nothing meaningful left to send back.
    ✅ Think carefully about cascade behavior before enabling it — ask “should this child data really disappear when the parent does?”
    ❌ Don’t reuse your Create schema for PATCH — a Create schema has required fields; a PATCH schema needs every field to be optional.
    ❌ Don’t forget that model_dump() without exclude_unset=True will include every field, including ones the client never sent, silently overwriting real data with None.
