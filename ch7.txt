Let’s Start With a Real Problem

In Chapter 6, we built a 404 response the “manual” way — a hand-written if user is None: return JSONResponse(...) block. It worked. But then the assignment quietly asked you to repeat that pattern for a DELETE endpoint and a duplicate-username check too.

Now imagine this app grown up: 40 endpoints, each with 2-3 possible error cases. That’s 100+ copies of nearly identical if ... return JSONResponse(status_code=..., content={"detail": ...}) blocks scattered across your codebase. One day, your team decides all error responses should also include an error_code field for the frontend. Now you have to find and update all 100+ of them, by hand, hoping you don’t miss one.

This is precisely the kind of repetitive, error-prone problem that frameworks are supposed to solve for you — and FastAPI does, beautifully, with exceptions and a global error handler. Let’s fix this once, properly, everywhere.

Each program below is a complete, standalone build — starting from project creation all the way to running and testing it. You can follow them in order, or jump straight to any program and build it on its own.
What You’ll Learn

    Why raising exceptions is cleaner than manually returning error responses
    How to use FastAPI’s built-in HTTPException
    How to design your own custom exception classes for domain-specific errors
    How to register a global exception handler that catches an exception anywhere in your app and formats the response consistently
    How to customize FastAPI’s default validation error (422) responses
    How to safely catch unexpected errors with a generic handler, without leaking internal details to the client
    Theory + hands-on assignment questions to lock in what you’ve learned

Theory: Exceptions vs. Manually Returning Responses

In Chapter 6, our error-handling code looked like this:

if user is None:
    return JSONResponse(status_code=404, content={"detail": "not found"})

This is a return-based approach — the function decides what response to send, right there, inline. It works for one endpoint, but it doesn’t scale, and it mixes two different concerns together: business logic (“does this user exist?”) and HTTP response formatting (“what JSON shape and status code do we send back?”).

FastAPI encourages a different approach: raise an exception when something goes wrong, and let a separate, centralized piece of code decide how to turn that exception into an HTTP response.

if user is None:
    raise HTTPException(status_code=404, detail="not found")

At first glance this looks like a small change. But it unlocks something powerful: you can raise this exception from anywhere — deep inside a service function, a dependency, even a database call — and FastAPI will still catch it and build the correct HTTP response, without that deeply nested code needing to know anything about JSONResponse or Response objects at all.

Explanation: The familiar In/Out schema pattern from Chapter 5 — UserOut keeps the password out of every response.

app/services/user_service.py

from app.schemas.user import UserCreate

_fake_users_db: list[dict] = []
_next_id = 1


def create_user(user_in: UserCreate) -> dict:
    global _next_id

    hashed_password = f"hashed_{user_in.password}"
    new_user = {
        "id": _next_id,
        "username": user_in.username,
        "email": user_in.email,
        "hashed_password": hashed_password,
        "is_active": True,
    }

    _fake_users_db.append(new_user)
    _next_id += 1
    return new_user


def get_user_by_id(user_id: int) -> dict | None:
    for user in _fake_users_db:
        if user["id"] == user_id:
            return user
    return None

Explanation: Same in-memory service layer style used in earlier chapters. get_user_by_id still returns None for a missing user at this stage — we’ll upgrade this in Program 2.

app/routers/users.py

from fastapi import APIRouter, HTTPException, status

from app.schemas.user import UserCreate, UserOut
from app.services.user_service import create_user, get_user_by_id

router = APIRouter(prefix="/users", tags=["Users"])


@router.post("/register", response_model=UserOut, status_code=status.HTTP_201_CREATED)
def register_user(user_in: UserCreate):
    return create_user(user_in)


@router.get("/{user_id}", response_model=UserOut)
def get_user(user_id: int):
    user = get_user_by_id(user_id)

    if user is None:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail=f"User with id {user_id} was not found.",
        )

    return user

Explanation:

    raise HTTPException(status_code=..., detail=...) — as soon as this line runs, FastAPI immediately stops executing the rest of the function and builds a proper JSON error response: {"detail": "User with id 999 was not found."} with the status code you specified.
    Compare this to Chapter 6’s version: no JSONResponse import, no manually built dictionary. The code reads much closer to plain English: “if there’s no user, raise a 404.”
    We no longer need to inject Response into this function at all — HTTPException handles response construction entirely on its own.

app/core/exceptions.py

class UserNotFoundError(Exception):
    """Raised when a requested user does not exist."""

    def __init__(self, user_id: int):
        self.user_id = user_id
        super().__init__(f"User with id {user_id} was not found.")


class UsernameAlreadyExistsError(Exception):
    """Raised when trying to register a username that's already taken."""

    def __init__(self, username: str):
        self.username = username
        super().__init__(f"Username '{username}' is already taken.")

Explanation:

    These are plain Python exceptions — nothing FastAPI-specific. Your service layer shouldn’t need to know anything about HTTP status codes or JSON. It just describes what went wrong, in its own vocabulary.
    Storing self.user_id / self.username lets whoever catches this exception later build a more detailed message if needed, instead of just a plain string.

app/main.py

from fastapi import FastAPI, Request, status
from fastapi.responses import JSONResponse

from app.core.exceptions import UserNotFoundError, UsernameAlreadyExistsError
from app.routers import users

app = FastAPI(
    title="FastAPI Global Handler Demo",
    version="1.0.0",
    description="Chapter 7 - Program 3: Global Exception Handlers",
)

app.include_router(users.router)


@app.exception_handler(UserNotFoundError)
def user_not_found_handler(request: Request, exc: UserNotFoundError):
    return JSONResponse(
        status_code=status.HTTP_404_NOT_FOUND,
        content={"error_code": "USER_NOT_FOUND", "detail": str(exc)},
    )


@app.exception_handler(UsernameAlreadyExistsError)
def username_exists_handler(request: Request, exc: UsernameAlreadyExistsError):
    return JSONResponse(
        status_code=status.HTTP_409_CONFLICT,
        content={"error_code": "USERNAME_TAKEN", "detail": str(exc)},
    )


@app.get("/", tags=["Root"])
def read_root():
    return {"message": "Welcome to the Global Handler Demo"}

Explanation:

    @app.exception_handler(UserNotFoundError) registers a function that runs automatically, anywhere in the app, whenever a UserNotFoundError is raised — whether it happens in a router, a service function, or three layers deep in a dependency.
    The handler always receives two arguments: the incoming request and the exc (the exception instance) — a fixed signature FastAPI expects.
    str(exc) gives us the message built in the exception’s __init__ — no need to duplicate that message here.
    We used 409 Conflict for UsernameAlreadyExistsError — a more semantically correct status code than 400, since the request itself is well-formed; it’s just in conflict with existing data.
    Every response also includes an error_code field — small, but useful for frontend teams, who can write if (error.error_code === "USER_NOT_FOUND") instead of matching on the human-readable message.
    This is the payoff: if tomorrow you need to add a new field to every error response, you update it in these one or two handler functions — not in a hundred scattered routes.

app/main.py

from fastapi import FastAPI, Request, status
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse

from app.core.exceptions import UserNotFoundError, UsernameAlreadyExistsError
from app.routers import users

app = FastAPI(
    title="FastAPI Full Error Handling Demo",
    version="1.0.0",
    description="Chapter 7 - Program 4: Validation Errors and Catch-All Handling",
)

app.include_router(users.router)


@app.exception_handler(UserNotFoundError)
def user_not_found_handler(request: Request, exc: UserNotFoundError):
    return JSONResponse(
        status_code=status.HTTP_404_NOT_FOUND,
        content={"error_code": "USER_NOT_FOUND", "detail": str(exc)},
    )


@app.exception_handler(UsernameAlreadyExistsError)
def username_exists_handler(request: Request, exc: UsernameAlreadyExistsError):
    return JSONResponse(
        status_code=status.HTTP_409_CONFLICT,
        content={"error_code": "USERNAME_TAKEN", "detail": str(exc)},
    )


@app.exception_handler(RequestValidationError)
def validation_exception_handler(request: Request, exc: RequestValidationError):
    return JSONResponse(
        status_code=status.HTTP_422_UNPROCESSABLE_ENTITY,
        content={
            "error_code": "VALIDATION_ERROR",
            "detail": exc.errors(),
        },
    )


@app.exception_handler(Exception)
def unhandled_exception_handler(request: Request, exc: Exception):
    # Log the real error internally so your team can investigate.
    print(f"Unhandled error: {exc!r}")

    return JSONResponse(
        status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
        content={
            "error_code": "INTERNAL_SERVER_ERROR",
            "detail": "Something went wrong on our end. Please try again later.",
        },
    )


@app.get("/", tags=["Root"])
def read_root():
    return {"message": "Welcome to the Full Error Handling Demo"}

Explanation:

    RequestValidationError is the exception FastAPI raises internally whenever incoming data fails Pydantic validation. By handling it ourselves, we reshape the response into our own error_code / detail format, matching our other error responses.
    exc.errors() returns Pydantic’s detailed list of exactly which fields failed and why — genuinely useful for debugging, so we keep it, just under our own response shape.
    @app.exception_handler(Exception) is a catch-all — it matches literally any exception not already handled by a more specific handler above it. This is your safety net against bugs you didn’t anticipate.
    We print() (in a real project, use proper logging) the real error internally, but return a generic, safe message to the client. Never expose raw stack traces, file paths, or internal exception messages — that information is a gift to attackers.

    ⚠️ Important: FastAPI matches handlers by exception type, not by decorator order. Still, always keep your catch-all Exception handler conceptually “last resort,” and make sure it never swallows details you actually wanted the client to see (FastAPI handles HTTPException separately by default, so this is safe here).

Tips & Instructions for Developers

    ✅ Keep your service layer free of HTTPException — raise plain, custom exceptions there, and let handlers registered in main.py translate them into HTTP responses.
    ✅ Give every custom exception a clear, descriptive name (UserNotFoundError, not Error1) — it should read like a sentence when raised: raise UserNotFoundError(user_id).
    ✅ Add an error_code (or similar machine-readable field) to your error responses — frontend teams will thank you for not having to string-match human-readable messages.
    ✅ Always include a catch-all Exception handler in production apps — an unhandled bug should never leak a stack trace to a client.
    ✅ Log the real error internally in your catch-all handler, even while returning a generic message externally — you still need to know what broke.
    ❌ Don’t put business logic decisions (“is this a 404 or a 409?”) inside your service functions — that’s an HTTP concern, and belongs in the exception handler, not the exception itself.
    ❌ Don’t reuse Python’s built-in exceptions (like ValueError) for domain errors if you can avoid it — a custom exception class is far easier to catch precisely and document.
